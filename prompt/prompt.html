1. Ground it in the code, not memory: read the relevant commits and the current

   state of the files before writing. If the conversation and the code disagree,

   the code wins.

2. Cover, in this order:

   - What it does and the problem it solves (2–3 sentences, plain English)

   - How it works end to end — the flow through the code, with real file paths

     and function names at each step

   - Settings, defaults, and thresholds, and where each lives

   - What changed vs the old behavior, if it replaced or modified something

   - Edge cases and failure modes it handles, plus known gaps

   - How to verify it works (commands to run, what output to expect)

3. If you're unsure whether something is true, check the code; if still unsure,

   mark it as uncertain rather than guessing. No invented behavior.

4. Audience: .

   It must stand alone — no conversation shorthand, no "as discussed above".
